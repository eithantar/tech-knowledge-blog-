# Web Development ဆိုတာဘာလဲ? အစပြုသူများအတွက် လမ်းညွှန်

> ဖတ်ရန်: [English](what-is-web-development-en.md) | **မြန်မာ**

[Web Application ဆောင်းပါး](../Web-Application/what-is-web-application-mm.md) မှာ Frontend, Backend, Database နဲ့ API တွေ စားသောက်ဆိုင်တစ်ဆိုင်လို ပူးပေါင်းအလုပ်လုပ်ပုံ၊ ဆိုလိုတာက **Web App တစ်ခု ဘယ်လိုအလုပ်လုပ်လဲ** ဆိုတာ လေ့လာခဲ့ပြီးပါပြီ။

ဒါပေမဲ့ အဲဒီ စားသောက်ဆိုင်ကို ဘယ်သူ ဆောက်တာလဲ? ဘယ်လို Plan ချ၊ Design ဆွဲ၊ Test လုပ်ပြီး လူအများအတွက် ဖွင့်လှစ်ကာ နေ့တိုင်း ဆက်လည်ပတ်နေအောင် လုပ်ကြတာလဲ?

ဒါကတော့ **Web Development** အကြောင်း ဖြစ်ပါတယ်။

## ၁။ Web Development ဆိုတာဘာလဲ?

**Web Development** ဆိုတာ Website နဲ့ Web Application တွေကို **တည်ဆောက်ခြင်း၊ Test လုပ်ခြင်း၊ Launch လုပ်ခြင်းနဲ့ ထိန်းသိမ်းခြင်း** လုပ်ငန်း ဖြစ်ပါတယ်။

Code ရေးတာထက် အများကြီး ပိုပါဝင်ပါတယ် -

- ဘာတည်ဆောက်မလဲ Plan ချတာ
- ဘယ်လိုပုံစံ၊ ဘယ်လိုခံစားရမလဲ Design ဆွဲတာ
- Frontend နဲ့ Backend Code ရေးတာ
- Database နဲ့ Server တွေ Setup လုပ်တာ
- အားလုံး အလုပ်လုပ်လား Test လုပ်တာ
- Online တင်တာ (Deployment)
- Launch ပြီးနောက် Bug ပြင်တာနဲ့ Feature အသစ်ထည့်တာ

ဒီအလုပ်ကို လုပ်တဲ့သူတွေကို **Web Developer** လို့ ခေါ်ပါတယ်။

## ၂။ စားသောက်ဆိုင် ဥပမာ – စားသောက်ဆိုင်တစ်ဆိုင် ဆောက်ခြင်း

Web Application က စားသောက်ဆိုင်တစ်ဆိုင်ဆိုရင် Web Development ကတော့ **အဲဒီဆိုင်ကို ဆောက်ပြီး လည်ပတ်စေတဲ့** လုပ်ငန်းတစ်ခုလုံး ဖြစ်ပါတယ်။

| စားသောက်ဆိုင် ဆောက်ခြင်း | Web Development |
|---|---|
| ဆိုင်ပုံစံ၊ Menu နဲ့ Budget ဆုံးဖြတ်တာ | **Planning** – Requirement နဲ့ ရည်မှန်းချက်များ |
| ဗိသုကာနဲ့ Interior Designer က ပုံစံဆွဲတာ | **UI/UX Design** – Layout, Color, User Flow |
| ထမင်းစားခန်းနဲ့ အလှဆင်တာကို ဆောက်တာ | **Frontend Development** |
| မီးဖိုချောင်၊ ရေပိုက်နဲ့ ပစ္စည်းတွေ တပ်ဆင်တာ | **Backend Development** |
| သိုလှောင်ခန်းကို စနစ်တကျ စီစဉ်တာ | **Database Design** |
| မဖွင့်ခင် ကျန်းမာရေး စစ်ဆေးတာနဲ့ အရသာ မြည်းစမ်းတာ | **Testing / QA** |
| ဆိုင်ဖွင့်ပွဲနေ့ | **Deployment / Launch** |
| လျှပ်စစ်၊ ရေနဲ့ အဆောက်အအုံ ထိန်းသိမ်းတာ | **DevOps / Operations** |
| Menu Update လုပ်တာ၊ ကျိုးနေတဲ့ ကုလားထိုင် ပြင်တာ | **Maintenance နဲ့ Feature အသစ်များ** |

စားသောက်ဆိုင်လိုပါပဲ Web App တစ်ခုဟာ တကယ်တမ်း "ပြီးသွားတယ်" ဆိုတာ မရှိပါဘူး။ ဆိုင်ဖွင့်ပြီးနောက်မှာလည်း Customer တွေရဲ့ အကြံပြုချက်အပေါ် မူတည်ပြီး ဆက်ပြီး တိုးတက်အောင် လုပ်နေရပါတယ်။

## ၃။ Web Development ရဲ့ အဓိက Role များ

| Role | ဘာလုပ်လဲ | စားသောက်ဆိုင် ဥပမာ |
|---|---|---|
| **Frontend Developer** | User မြင်ပြီး အသုံးပြုရတဲ့ အပိုင်းကို တည်ဆောက်တယ် (HTML, CSS, JavaScript, React) | ထမင်းစားခန်းကို ဆောက်တယ် |
| **Backend Developer** | Server, API, Business Logic နဲ့ Database ကို တည်ဆောက်တယ် (Python, Node.js, Java) | မီးဖိုချောင်ကို ဆောက်တယ် |
| **Full-Stack Developer** | Frontend ရော Backend ရော လုပ်တယ် | ထမင်းစားခန်းရော မီးဖိုချောင်ရော ဆောက်နိုင်တယ် |
| **UI/UX Designer** | App ရဲ့ ပုံစံ (UI) နဲ့ သုံးရလွယ်မှု (UX) ကို Design ဆွဲတယ် | ဗိသုကာနဲ့ Interior Designer |
| **QA / Test Engineer** | User တွေ မတွေ့ခင် Bug တွေကို ရှာတယ် | ကျန်းမာရေး စစ်ဆေးသူနဲ့ အရသာ မြည်းစမ်းသူ |
| **DevOps / Cloud Engineer** | Server, Deployment, Monitoring နဲ့ Scaling ကို စီမံတယ် | မီးနဲ့ ရေ ပုံမှန်ရနေအောင် ထိန်းတဲ့ အဆောက်အအုံ Manager |

အဖွဲ့သေးတွေနဲ့ Startup တွေမှာ လူတစ်ယောက်က Role အများကြီးကို လုပ်လေ့ရှိပါတယ်။ ကုမ္ပဏီကြီးတွေမှာတော့ Role တစ်ခုချင်းစီက Team တစ်ခုလုံး ဖြစ်နိုင်ပါတယ်။

## ၄။ Web Development လုပ်ငန်းစဉ်

Project အများစုဟာ **Software Development Life Cycle (SDLC)** လို့ခေါ်တဲ့ လည်ပတ်မှုတစ်ခုကို လိုက်နာကြပါတယ်။

```
  ┌──────────┐    ┌──────────┐    ┌─────────────┐
  │ 1. Plan  │ ─► │ 2. Design│ ─► │ 3. Develop  │
  └──────────┘    └──────────┘    └─────────────┘
       ▲                                 │
       │                                 ▼
  ┌──────────────┐  ┌──────────┐  ┌──────────┐
  │ 6. Maintain  │◄─│ 5. Deploy│◄─│ 4. Test  │
  └──────────────┘  └──────────┘  └──────────┘
```

**၁။ Plan**

ဘယ်ပြဿနာကို ဖြေရှင်းမှာလဲ? User တွေက ဘယ်သူတွေလဲ? ဘယ် Feature တွေကို အရင်လိုအပ်လဲ? Budget နဲ့ Deadline က ဘယ်လောက်လဲ?

*ဥပမာ:* "Player တွေက Leaderboard ကြည့်ပြီး ကိုယ့် Score ကို ထည့်ချင်တယ်။"

**၂။ Design**

**Figma** လို Tool တွေနဲ့ **Wireframe** (Page တစ်ခုချင်းစီရဲ့ ရိုးရှင်းတဲ့ ပုံကြမ်း) နဲ့ **Mockup** (Color နဲ့ Font ပါတဲ့ အသေးစိတ် Design) တွေ ဆွဲပါတယ်။ Database Table တွေနဲ့ API Endpoint တွေကိုလည်း Plan ချပါတယ်။

**၃။ Develop**

Frontend နဲ့ Backend Code ရေး၊ Database Setup လုပ်ပြီး API ကနေ အားလုံးကို ချိတ်ဆက်ပါတယ်။

**၄။ Test**

Feature တွေ အလုပ်လုပ်လား၊ အဟောင်းတွေ ပျက်မသွားဘူးလား၊ Browser နဲ့ Screen Size အမျိုးမျိုးမှာ အဆင်ပြေလား စစ်ဆေးပါတယ်။

**၅။ Deploy**

တကယ့် User တွေ သုံးနိုင်အောင် App ကို Server ပေါ် တင်ပါတယ်။

**၆။ Maintain**

Bug ပြင်တယ်၊ Security အတွက် Library တွေ Update လုပ်တယ်၊ Performance ကို စောင့်ကြည့်တယ်၊ User Feedback အပေါ် မူတည်ပြီး Feature အသစ်တွေ ထည့်တယ်။ ပြီးရင် လည်ပတ်မှု ပြန်စပါတယ်။

ဒီနေ့ခေတ် Team အများစုက **Sprint** လို့ခေါ်တဲ့ ၁–၂ ပတ်ကြာ လည်ပတ်မှုတိုလေးတွေနဲ့ အလုပ်လုပ်ကြပါတယ်။ ဒီနည်းလမ်းကို **Agile** လို့ ခေါ်ပါတယ်။ အားလုံးကို တစ်ခါတည်း တည်ဆောက်မယ့်အစား အပိုင်းသေးလေး တစ်ခု တည်ဆောက်၊ Release လုပ်၊ Feedback ယူပြီး တိုးတက်အောင် လုပ်သွားတာပါ။

## ၅။ Web Developer တွေအတွက် မရှိမဖြစ် Tool များ

| Tool | ဘာအတွက်လဲ | ဥပမာ |
|---|---|---|
| **Code Editor** | Code ရေးဖို့ | VS Code, WebStorm |
| **Browser DevTools** | HTML/CSS စစ်ဆေးတာ၊ JavaScript Debug လုပ်တာ၊ Network Request တွေ ကြည့်တာ | Chrome DevTools (F12 နှိပ်ပါ) |
| **Terminal** | Command, Server နဲ့ Script တွေ Run ဖို့ | Bash, PowerShell, Zsh |
| **Version Control** | ပြောင်းလဲမှုတွေကို မှတ်တမ်းတင်ပြီး Team နဲ့ အလုပ်လုပ်ဖို့ | Git, GitHub, GitLab |
| **Package Manager** | Library တွေ Install လုပ်ဖို့ | npm (JavaScript), pip (Python) |
| **API Testing** | API တွေဆီ Test Request ပို့ဖို့ | Postman, curl, Bruno |
| **Design** | Design တွေ ဖန်တီးပြီး မျှဝေဖို့ | Figma |
| **Container** | နေရာတိုင်းမှာ Environment အတူတူ Run ဖို့ | Docker ([Docker ဆောင်းပါး](../Docker/docker-and-docker-compose-mm.md) ကို ကြည့်ပါ) |
| **AI Coding Assistant** | Code ရှင်းပြတာ၊ Code ရေးတာ၊ Bug ရှာတာ | GitHub Copilot, Claude, ChatGPT |

**အကြံပြုချက်:** **Browser DevTools** ကို စောစော လေ့လာပါ။ Browser မှာ `F12` နှိပ်လိုက်ရင် HTML Element တိုင်းကို ကြည့်နိုင်တယ်၊ CSS ကို Live ပြင်နိုင်တယ်၊ JavaScript Error တွေကို ဖတ်နိုင်ပြီး ကိုယ့် Page က API ဆီ ပို့တဲ့ Request တိုင်းကို စောင့်ကြည့်နိုင်ပါတယ်။

## ၆။ Development Environment များ

Professional Team တွေက များသောအားဖြင့် App ကို အနည်းဆုံး နေရာ ၃ ခုမှာ Run ကြပါတယ် -

| Environment | ဘယ်သူသုံးလဲ | ရည်ရွယ်ချက် |
|---|---|---|
| **Local (Development)** | Developer ကိုယ်တိုင် ကိုယ့် Computer ပေါ်မှာ | Code ရေးပြီး စမ်းကြည့်ဖို့ |
| **Staging** | Team နဲ့ Tester တွေ | နောက်ဆုံး Test လုပ်ဖို့ Production ရဲ့ မိတ္တူ |
| **Production** | တကယ့် User တွေ | Live App |

Staging ကို စားသောက်ဆိုင် ဖွင့်ပွဲမတိုင်ခင် **အစမ်းလေ့ကျင့်တာ** လို့ စဉ်းစားကြည့်ပါ။ တကယ့် Customer တွေ မရောက်ခင် ပြဿနာတွေကို ပြင်နိုင်အောင် သူငယ်ချင်းနဲ့ မိသားစုတွေကို အရင် ဖိတ်ကျွေးတာမျိုးပါ။

**ရွှေစည်းမျဉ်း:** Code အသစ်ကို Production မှာ တိုက်ရိုက် ဘယ်တော့မှ Test မလုပ်ပါနဲ့။

## ၇။ Git နဲ့ Team အဖြစ် အလုပ်လုပ်ခြင်း

**Git** က ကိုယ့် Code ရဲ့ ပြောင်းလဲမှုတိုင်းကို မှတ်တမ်းတင်ထားတဲ့အတွက် ဘယ်သူ ဘာပြောင်းခဲ့လဲ ကြည့်နိုင်တယ်၊ Version အဟောင်းကို ပြန်သွားနိုင်တယ်၊ တခြားသူတွေရဲ့ အလုပ်ကို ထပ်မရေးမိဘဲ အတူတူ အလုပ်လုပ်နိုင်ပါတယ်။

ပုံမှန် Team Workflow တစ်ခု -

```bash
# ၁။ နောက်ဆုံး Code ကို ယူမယ်
git checkout main
git pull

# ၂။ ကိုယ့် Feature အတွက် Branch အသစ် ဖန်တီးမယ်
git checkout -b feature/add-search-box

# ၃။ Code ရေးပြီး ပြောင်းလဲမှုတွေကို သိမ်းမယ်
git add .
git commit -m "Add search box to leaderboard"

# ၄။ ကိုယ့် Branch ကို Upload လုပ်မယ်
git push -u origin feature/add-search-box
```

**၅။ GitHub မှာ Pull Request (PR) ဖွင့်ပါ။** အဖွဲ့သားတစ်ယောက်က ကိုယ့် Code ကို Review လုပ်၊ Comment ပေးပြီး Approve လုပ်ပါတယ်။

**၆။ PR ကို `main` ထဲ Merge လုပ်ပါ။** ကိုယ့် Feature က Project ရဲ့ အစိတ်အပိုင်း ဖြစ်သွားပါပြီ။

ဒါက စားဖိုမှူးတစ်ယောက်က ဟင်းချက်နည်းအသစ်ကို စမ်းသပ်မီးဖိုချောင်မှာ စမ်းချက်၊ စားဖိုမှူးချုပ်ကို မြည်းခိုင်းပြီးမှ တကယ့် Menu ထဲ ထည့်တာနဲ့ တူပါတယ်။

## ၈။ ကောင်းမွန်တဲ့ Website တည်ဆောက်ခြင်း – "အလုပ်လုပ်တယ်" ထက် ပိုပြီး

Professional Web App တစ်ခုဟာ အလုပ်လုပ်ရုံနဲ့ မလုံလောက်ပါဘူး။ အောက်ပါအတိုင်းလည်း ဖြစ်ရပါမယ် -

**၁။ Responsive – Screen Size တိုင်းမှာ အဆင်ပြေရမယ်**

Web Traffic ရဲ့ တစ်ဝက်ကျော်က Phone တွေကနေ လာပါတယ်။ Responsive Design က Layout ကို အလိုအလျောက် ချိန်ညှိပေးပါတယ်။

```css
/* Screen ကြီးတွေမှာ Column ၃ ခု */
.cards {
  display: grid;
  grid-template-columns: repeat(3, 1fr);
  gap: 16px;
```

**၂။ Accessible – လူတိုင်း သုံးနိုင်ရမယ်**

အမြင်၊ အကြား ဒါမှမဟုတ် လှုပ်ရှားမှု မသန်စွမ်းသူတွေလည်း Web ကို သုံးကြပါတယ်။ Accessibility (**a11y** လို့ မကြာခဏ ရေးကြတယ်) ဆိုတာ -

- Screen Reader တွေအတွက် ပုံတွေမှာ `alt` Text ထည့်တာ
- Color Contrast လုံလောက်အောင် သုံးတာ
- Keyboard နဲ့ အားလုံးကို သုံးလို့ရအောင် လုပ်တာ
- အရာအားလုံးအတွက် `<div>` မသုံးဘဲ မှန်ကန်တဲ့ HTML Element တွေ (`<button>`, `<nav>`, `<h1>`) ကို သုံးတာ

```html
<!-- ❌ မကောင်းဘူး -->
<img src="trophy.png">
<div onclick="save()">Save</div>

<!-- ✅ ကောင်းတယ် -->
<img src="trophy.png" alt="Gold trophy for first place">
<button onclick="save()">Save</button>
```

## ၉။ Testing

Testing ဆိုတာ **ကိုယ့် Code ကို စစ်ဆေးပေးမယ့် Code** ရေးတာ ဖြစ်ပါတယ်။ နောက်ပိုင်း တစ်ခုခု ပြောင်းလိုက်တဲ့အခါ တစ်ခုခု ပျက်သွားရင် Test တွေက ချက်ချင်း ပြောပြပါတယ်။

| Test အမျိုးအစား | ဘာကို စစ်လဲ | စားသောက်ဆိုင် ဥပမာ |
|---|---|---|
| **Unit Test** | Function သေးသေးလေး တစ်ခု | Sauce က ငန်လောက်ရဲ့လား? |
| **Integration Test** | အစိတ်အပိုင်း အများကြီး ပူးပေါင်းအလုပ်လုပ်တာ (ဥပမာ API + Database) | Sauce နဲ့ ခေါက်ဆွဲ ပေါင်းလိုက်ရင် အရသာ မှန်ရဲ့လား? |
| **End-to-End (E2E) Test** | တကယ့် User တစ်ယောက်လို Browser မှာ နှိပ်ပြီး App တစ်ခုလုံးကို စစ်တာ | လျှို့ဝှက် Customer တစ်ယောက်က မှာ၊ စား၊ ငွေရှင်းတာ |

**ဥပမာ: Web Application ဆောင်းပါးက Leaderboard API ကို** **pytest** နဲ့ Test လုပ်ခြင်း -

**test_main.py**

```python
from fastapi.testclient import TestClient

from main import app

client = TestClient(app)


def test_add_score():
    response = client.post("/api/scores", json={"player": "Tester", "score": 100})
    assert response.status_code == 201
    assert response.json()["player"] == "Tester"


def test_scores_are_sorted_highest_first():
    client.post("/api/scores", json={"player": "Low", "score": 1})
    client.post("/api/scores", json={"player": "High", "score": 9999})

    scores = [s["score"] for s in client.get("/api/scores").json()]
    assert scores == sorted(scores, reverse=True)


def test_invalid_score_is_rejected():
    response = client.post("/api/scores", json={"player": "Cheater", "score": "lots"})
    assert response.status_code == 422
```

```bash
pip install pytest httpx
pytest
```

- **Python:** pytest
- **JavaScript:** Jest, Vitest
- **End-to-end (Browser):** Playwright, Cypress

## ၁၀။ CI/CD – အလိုအလျောက် Test နဲ့ Deploy လုပ်ခြင်း

**CI/CD** ဆိုတာ **Continuous Integration / Continuous Deployment** ရဲ့ အတိုကောက် ဖြစ်ပါတယ်။

- **Continuous Integration (CI)** – တစ်ယောက်ယောက် Code Push လုပ်တိုင်း Test တွေ **အလိုအလျောက်** Run ပါတယ်။
- **Continuous Deployment (CD)** – Test တွေ Pass ဖြစ်ရင် Version အသစ်ကို **အလိုအလျောက်** Deploy လုပ်ပါတယ်။

လူတစ်ယောက်က Test Run ဖို့နဲ့ File တွေ Upload လုပ်ဖို့ မှတ်ထားရမယ့်အစား စက်ရုပ်က အကြိမ်တိုင်း လုပ်ပေးပါတယ်။

**ဥပမာ: GitHub Actions** – ဒီ File ကို ကိုယ့် Project ထဲမှာ `.github/workflows/tests.yml` အဖြစ် သိမ်းပါ -

```yaml
name: Tests

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install dependencies
        run: pip install fastapi uvicorn pytest httpx

      - name: Run tests
        run: pytest
```

အခုဆိုရင် Push တိုင်းနဲ့ Pull Request တိုင်းမှာ GitHub ပေါ်မှာ ✅ ဒါမှမဟုတ် ❌ ပြပါလိမ့်မယ်။ Team တွေက များသောအားဖြင့် Test တွေ Pass မဖြစ်မချင်း Pull Request ကို Merge လုပ်ခွင့် မပေးပါဘူး။

## ၁၁။ လူကြိုက်များတဲ့ Tech Stack များ

**Tech Stack** ဆိုတာ App တစ်ခု တည်ဆောက်ဖို့ တွဲသုံးတဲ့ နည်းပညာ အစုအဝေး ဖြစ်ပါတယ်။

|---|---|---|---|---|

| **Python Stack** | React ဒါမှမဟုတ် HTML Template | Django ဒါမှမဟုတ် FastAPI | PostgreSQL | Data များတဲ့ App၊ AI Integration |

**"အကောင်းဆုံး" Stack ဆိုတာ မရှိပါဘူး။** တစ်ခုကို ရွေး၊ ကောင်းကောင်း လေ့လာပြီး တကယ့် Project တွေ တည်ဆောက်ပါ။ Concept တွေကို နားလည်သွားရင် တခြား Stack ကို ပြောင်းတာ အများကြီး ပိုလွယ်သွားပါတယ်။

AI Tool တွေဟာ အခုဆိုရင် နေ့စဉ် Web Development ရဲ့ အစိတ်အပိုင်း ဖြစ်လာပါပြီ -

- **လေ့လာခြင်း** – လေ့လာရင်း မေးခွန်းတွေ မေးတာ

ဒါပေမဲ့ AI က မှားနိုင်ပါတယ် ([Prompt Engineering ဆောင်းပါး](../Artificial-Intelligence/prompt-engineering-mm.md) ထဲက "Hallucination" ကို ကြည့်ပါ)။ အမြဲတမ်း -

- အထူးသဖြင့် Authentication နဲ့ Database Code တွေမှာ **Security ကို စစ်ပါ**

AI က Developer ကောင်းတွေကို ပိုမြန်စေပါတယ်။ ဒါပေမဲ့ Fundamental တွေကို နားလည်ထားဖို့ လိုအပ်ချက်ကို အစားမထိုးနိုင်ပါဘူး။
