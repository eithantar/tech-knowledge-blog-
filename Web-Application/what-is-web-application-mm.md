# Web Application ဆိုတာဘာလဲ။ ဘယ်လိုအလုပ်လုပ်သလဲ?

> ဖတ်ရန်: [English](what-is-web-application-en.md) | **မြန်မာ**

နေ့စဉ် Browser ထဲမှာ သုံးနေတဲ့ App တွေကို စဉ်းစားကြည့်ပါ - Gmail, Facebook, YouTube, Online Banking, Google Docs ဒါမှမဟုတ် Online Shopping Website တွေပါ။

ဒါတွေကို ဘာမှ Install လုပ်စရာ မလိုပါဘူး။ Browser ဖွင့်၊ လိပ်စာရိုက်ပြီး သုံးလို့ရပါပြီ။ ကိုယ့် Account ကို မှတ်ထားပေးတယ်၊ ကိုယ့် Data ကို ပြပေးတယ်၊ Button နှိပ်တာနဲ့ Update ဖြစ်သွားတယ်။

ဒါတွေအားလုံးဟာ **Web Application** တွေ ဖြစ်ပါတယ်။

## ၁။ Web Application ဆိုတာဘာလဲ?

**Web Application (Web App)** ဆိုတာ **Server** ပေါ်မှာ Run နေပြီး Internet ကနေတစ်ဆင့် **Web Browser** နဲ့ အသုံးပြုရတဲ့ Software Program တစ်ခု ဖြစ်ပါတယ်။

- **Install လုပ်စရာမလို** – Browser ဖွင့်ပြီး URL ကို သွားရုံပါပဲ။
- **နေရာတိုင်းမှာ အလုပ်လုပ်** – Windows, Mac, Linux, Phone, Tablet အားလုံးမှာ Browser ရှိပါတယ်။
- **အမြဲတမ်း နောက်ဆုံး Version** – Developer က Server ကို Update လုပ်လိုက်တာနဲ့ User တိုင်း Version အသစ်ကို ချက်ချင်း ရပါတယ်။
- **Data တွေကို Server ပေါ်မှာ သိမ်းထား** – ဘယ် Device ကနေ Login ဝင်ဝင် ကိုယ့် Data တွေ ရှိနေပါတယ်။

## ၂။ Website နဲ့ Web Application ဘာကွာလဲ?

ဒီစကားလုံး နှစ်ခုကို အဓိပ္ပာယ်တူသလို သုံးလေ့ရှိကြပေမဲ့ ကွာခြားချက် ရှိပါတယ်။

| | Website | Web Application |
|---|---|---|
| အဓိက ရည်ရွယ်ချက် | အချက်အလက် ပြသဖို့ | User တွေ တစ်ခုခု **လုပ်ဆောင်** နိုင်ဖို့ |
| Interaction | အများအားဖြင့် ဖတ်ရုံ | Login ဝင်တာ၊ ဖန်တီးတာ၊ ပြင်တာ၊ ဝယ်တာ |
| Content | လူတိုင်းအတွက် အတူတူ | User တစ်ယောက်ချင်းစီအတွက် မတူဘူး |
| ဥပမာ | ကုမ္ပဏီရဲ့ "About Us" Page, Blog | Gmail, Online Banking, Facebook |

အလွယ်မှတ်နည်း - **Website က စားသောက်ဆိုင်ရဲ့ Menu Board လိုဖြစ်ပြီး Web Application ကတော့ တကယ် အစားအသောက် မှာစားလို့ရတဲ့ စားသောက်ဆိုင် တစ်ဆိုင်လုံး ဖြစ်ပါတယ်။**

လက်တွေ့မှာတော့ နှစ်ခုကြားမှာ ရောနေတတ်ပါတယ်။ ဥပမာ Blog တစ်ခုမှာ Login နဲ့ Comment ထည့်လိုက်ရင် Web App ဖြစ်လာပါပြီ။

## ၃။ စားသောက်ဆိုင် ဥပမာ

[API ဆောင်းပါး](../API/what-is-api-mm.md) မှာ API ကို စားသောက်ဆိုင်က စားပွဲထိုးနဲ့ နှိုင်းယှဉ်ခဲ့ပါတယ်။ အခု **စားသောက်ဆိုင် တစ်ဆိုင်လုံး** ကို ကြည့်ရအောင်။ Web Application မှာလည်း အဲဒီလို အစိတ်အပိုင်းတွေ ရှိပါတယ်။

| စားသောက်ဆိုင် | Web Application | ဘာလုပ်လဲ |
|---|---|---|
| ထမင်းစားခန်း၊ စားပွဲ၊ Menu၊ အလှဆင်ထားတာ | **Frontend** | User မြင်ရပြီး နှိပ်ရတဲ့ အပိုင်း |
| စားပွဲထိုး | **API** | Frontend နဲ့ Backend ကြား Request နဲ့ Response သယ်ပေးတယ် |
| မီးဖိုချောင်နဲ့ စားဖိုမှူးတွေ | **Backend** | Request တွေကို စီမံပြီး Business Rule တွေ အကောင်အထည်ဖော်တယ် |
| ပစ္စည်းသိုလှောင်ခန်း | **Database** | Data တွေကို အမြဲတမ်း သိမ်းထားတယ် |
| အဆောက်အအုံ | **Server / Hosting** | App Run နေတဲ့ Computer |
| လမ်းလိပ်စာ | **Domain Name** (ဥပမာ `myshop.com`) | လူတွေ App ကို ရှာတွေ့ဖို့ |
| လိပ်စာစာအုပ် | **DNS** | Domain Name ကို Server ရဲ့ IP Address အဖြစ် ပြောင်းပေးတယ် |

Customer က ထမင်းစားခန်း (Frontend) ကိုပဲ မြင်ရပါတယ်။ ဒါပေမဲ့ မီးဖိုချောင် (Backend) နဲ့ သိုလှောင်ခန်း (Database) မရှိရင် အစားအသောက် ဘယ်တော့မှ ရမှာ မဟုတ်ပါဘူး။

## ၄။ Web Application Architecture

Web Application အများစုဟာ အခြေခံ ဖွဲ့စည်းပုံ အတူတူပဲ ရှိပါတယ် -

```
┌──────────────┐        ┌──────────────┐        ┌──────────────┐
│   Browser    │  HTTP  │   Backend    │  SQL   │   Database   │
│  (Frontend)  │ ─────► │   (Server)   │ ─────► │              │
│ HTML/CSS/JS  │ ◄───── │ Python, Node │ ◄───── │  PostgreSQL  │
└──────────────┘  JSON  └──────────────┘  Data  └──────────────┘
     Client                                         
```

ဒါကို **Three-tier Architecture** လို့ ခေါ်လေ့ရှိပါတယ် -

1. **Presentation Tier** – Browser ထဲက Frontend။
2. **Application Tier** – Business Logic ပါတဲ့ Backend။
3. **Data Tier** – Database။

## ၅။ Web App တစ်ခုကို ဖွင့်လိုက်တဲ့အခါ ဘာတွေဖြစ်သွားလဲ?

`https://myshop.com` လို့ ရိုက်ပြီး Enter နှိပ်လိုက်တဲ့အခါ ဘာဖြစ်လဲဆိုတာ လိုက်ကြည့်ရအောင်။

**အဆင့် ၁ – Server ကို ရှာမယ် (DNS)**

Browser က DNS ကို "`myshop.com` ရဲ့ IP Address က ဘာလဲ?" လို့ မေးပါတယ်။ DNS က `203.0.113.10` လိုမျိုး ပြန်ဖြေပါတယ်။ စားသောက်ဆိုင် မသွားခင် လိပ်စာ ရှာကြည့်တာနဲ့ တူပါတယ်။

**အဆင့် ၂ – လုံခြုံစွာ ချိတ်ဆက်မယ် (HTTPS)**

Browser က Server နဲ့ ချိတ်ဆက်ပြီး Encryption ပြင်ဆင်ပါတယ်။ ဒါကြောင့် လမ်းမှာ Data တွေကို ဘယ်သူမှ ဖတ်လို့ မရပါဘူး။

**အဆင့် ၃ – Request ပို့မယ် (HTTP)**

Browser က Home Page ကို တောင်းဖို့ `GET /` ကို ပို့ပါတယ်။

**အဆင့် ၄ – Backend က အလုပ်လုပ်မယ်**

Backend က ကိုယ်ဘယ်သူလဲ စစ်ပြီး Database ထဲကနေ ကိုယ့် Data (ဥပမာ Shopping Cart) ကို ယူကာ Response ကို ပြင်ဆင်ပါတယ်။

**အဆင့် ၅ – Response ပြန်ပို့မယ်**

Server က HTML, CSS, JavaScript နဲ့ Data (များသောအားဖြင့် JSON) တွေကို ပြန်ပို့ပါတယ်။

**အဆင့် ၆ – Browser က Page ကို ပြမယ်**

Browser က Page ကို Screen ပေါ်မှာ ဆွဲပြပါတယ်။ Button တစ်ခု နှိပ်လိုက်ရင် JavaScript က Backend ရဲ့ API ဆီ Request အသစ်တွေ ပို့ပြီး ဒီလုပ်ငန်းစဉ် ဆက်ဖြစ်နေပါတယ်။

ဒါတွေအားလုံး များသောအားဖြင့် **တစ်စက္ကန့်အောက်** မှာ ဖြစ်သွားပါတယ်။

## ၆။ Frontend – User မြင်ရတဲ့အပိုင်း

Frontend က **Browser ထဲမှာ** Run ပါတယ်။ အဓိက နည်းပညာ ၃ ခုနဲ့ တည်ဆောက်ပါတယ် -

| နည်းပညာ | တာဝန် | စားသောက်ဆိုင် ဥပမာ |
|---|---|---|
| **HTML** | ဖွဲ့စည်းပုံနဲ့ Content | စားပွဲ၊ ကုလားထိုင်နဲ့ Menu |
| **CSS** | Design နဲ့ Layout | ဆေးအရောင်၊ မီးအလင်းနဲ့ အလှဆင်ထားတာ |
| **JavaScript** | အပြုအမူနဲ့ Interaction | ခေါ်လိုက်တာနဲ့ လာတဲ့ စားပွဲထိုး |

```html
<!-- HTML: ဖွဲ့စည်းပုံ -->
<button id="like">❤️ Like</button>
<span id="count">0</span>

<!-- CSS: Design -->
<style>
  #like { background: hotpink; color: white; border: none; padding: 8px 16px; }
</style>

<!-- JavaScript: အပြုအမူ -->
<script>
  let likes = 0;
  document.getElementById("like").addEventListener("click", () => {
    likes++;
    document.getElementById("count").textContent = likes;
  });
</script>
```

App ကြီးတွေအတွက်တော့ ရှုပ်ထွေးတဲ့ User Interface တွေကို လွယ်လွယ်ကူကူ တည်ဆောက်နိုင်အောင် **Frontend Framework** တွေကို သုံးကြပါတယ် -

- **React** (Meta) – လူသုံးအများဆုံး။
- **Vue** – လေ့လာရ လွယ်တယ်။
- **Angular** (Google) – ကုမ္ပဏီကြီးတွေမှာ လူကြိုက်များတယ်။
- **Svelte** – ပေါ့ပါးပြီး မြန်တယ်။

## ၇။ Backend – မီးဖိုချောင်

Backend က **Server ပေါ်မှာ** Run ပါတယ်။ User တွေ တိုက်ရိုက် မမြင်ရပါဘူး။ သူ့တာဝန်တွေကတော့ -

- **Business Logic** – "ဒီပစ္စည်း Stock ရှိသေးလား?"၊ "Member တွေကို 10% Discount ပေးမယ်"။
- **Authentication** – Username နဲ့ Password စစ်ဆေးတာ၊ Login တွေ စီမံတာ။
- **Database နဲ့ ဆက်သွယ်တာ** – Data သိမ်းတာ၊ ဖတ်တာ။
- **API ပေးတာ** – Frontend ဆီ Data ပို့ပေးတာ။
- **တခြား Service တွေနဲ့ ဆက်သွယ်တာ** – Payment, Email, AI Model စသည်။

လူကြိုက်များတဲ့ Backend Language နဲ့ Framework တွေ -

| Language | Framework |
|---|---|
| **Python** | Django, FastAPI, Flask |
| **JavaScript / TypeScript** | Node.js နဲ့ Express, NestJS, Next.js |
| **Java** | Spring Boot |
| **PHP** | Laravel |
| **Go** | Gin, Echo |
| **C#** | ASP.NET Core |

## ၈။ Database – သိုလှောင်ခန်း

Database က User Account, Product, Order, Message, Score စတဲ့ Data တွေကို အမြဲတမ်း သိမ်းထားပါတယ်။

**SQL (Relational) Database** တွေက Data တွေကို Spreadsheet လို Row နဲ့ Column ပါတဲ့ **Table** တွေထဲမှာ သိမ်းပါတယ်။

- ဥပမာ: **PostgreSQL, MySQL, SQLite**
- သင့်တော်တဲ့နေရာ: User, Order, Payment လို ဆက်စပ်မှု ရှင်းလင်းတဲ့ Data တွေ။

| id | player | score |
|---|---|---|
| 1 | Aung | 1500 |
| 2 | Su | 1200 |

**NoSQL Database** တွေကတော့ JSON လို Document ဒါမှမဟုတ် Key-Value လို ပိုပြီး ပြောင်းလွယ်တဲ့ ပုံစံတွေနဲ့ Data သိမ်းပါတယ်။

- ဥပမာ: **MongoDB** (Document), **Redis** (Key-Value၊ အရမ်းမြန်တယ်၊ Caching အတွက် သုံးလေ့ရှိတယ်)
- သင့်တော်တဲ့နေရာ: ပုံစံ ပြောင်းလဲလွယ်တဲ့ Data, Real-time Feature နဲ့ အရမ်းကြီးမားတဲ့ Scale။

## ၉။ Web Application အမျိုးအစားများ

**၁။ Multi-Page Application (MPA)**

Click တိုင်းမှာ Server ကနေ **Page အသစ်** တစ်ခု Load လုပ်ပါတယ်။ ရိုးရာ နည်းလမ်း ဖြစ်ပါတယ်။

- ဥပမာ: သတင်း Website အများစု၊ အစိုးရ Website တွေ၊ ရိုးရာ E-commerce Site တွေ။
- သင့်တော်တဲ့နေရာ: Content များတဲ့ Site တွေနဲ့ SEO (Google မှာ ရှာတွေ့နိုင်ဖို့)။

**၂။ Single-Page Application (SPA)**

Browser က **Page တစ်ခုတည်း** ကို တစ်ခါပဲ Load လုပ်ပါတယ်။ ပြီးရင် JavaScript က API ကနေ Data ယူပြီး ပြောင်းလဲတဲ့ အပိုင်းကိုပဲ Update လုပ်ပါတယ်။

- ဥပမာ: Gmail, Google Maps, Trello။
- သင့်တော်တဲ့နေရာ: App လို ချောမွေ့တဲ့ အတွေ့အကြုံ။

**၃။ Progressive Web App (PWA)**

Mobile App လိုပဲ Phone ရဲ့ Home Screen ပေါ် **Install** လုပ်လို့ရ၊ **Offline** အလုပ်လုပ်နိုင်ပြီး **Notification** ပို့နိုင်တဲ့ Web App ဖြစ်ပါတယ်။

- ဥပမာ: Twitter/X Lite, Starbucks PWA။
- သင့်တော်တဲ့နေရာ: Internet နှေးတဲ့ ဒါမှမဟုတ် မတည်ငြိမ်တဲ့ Mobile User တွေ။

**Next.js** နဲ့ **Nuxt** လို ခေတ်မီ Framework တွေက ဒီနည်းလမ်းတွေကို ရောသုံးပါတယ်။ ဥပမာ မြန်ဆန်ဖို့နဲ့ SEO အတွက် ပထမ Page ကို Server ပေါ်မှာ Render လုပ်ပြီး ပြီးရင် SPA လို အလုပ်လုပ်ပါတယ်။

## ၁၀။ ဥပမာ - Web Application သေးသေးလေး တစ်ခု တည်ဆောက်ခြင်း

ပြည့်စုံတဲ့ Mini Web App တစ်ခုဖြစ်တဲ့ **Game Leaderboard** ကို တည်ဆောက်ကြည့်ရအောင်။ အပိုင်း ၃ ပိုင်းစလုံး ပါဝင်ပါတယ် -

- **Frontend** – Player တွေ Score ထည့်ပြီး Top 10 ကို ကြည့်နိုင်တဲ့ HTML Page။
- **Backend** – API ပါတဲ့ FastAPI Server။
- **Database** – SQLite (File တစ်ခုတည်းထဲမှာ သိမ်းတဲ့ Database သေးသေးလေး၊ Python မှာ ပါပြီးသား)။

**Project ဖွဲ့စည်းပုံ**

```
leaderboard/
├── main.py       # Backend + Database
└── index.html    # Frontend
```

**main.py** (မီးဖိုချောင်နဲ့ သိုလှောင်ခန်း)

```python
import sqlite3

from fastapi import FastAPI
from fastapi.responses import FileResponse
from pydantic import BaseModel

app = FastAPI()
DB_FILE = "leaderboard.db"


def get_db():
    conn = sqlite3.connect(DB_FILE)
    conn.row_factory = sqlite3.Row
    return conn


# App စတဲ့အခါ Table ကို ဖန်တီးမယ်
with get_db() as conn:
    conn.execute("CREATE TABLE IF NOT EXISTS scores (player TEXT, score INTEGER)")


class Score(BaseModel):
    player: str
    score: int


# Frontend: HTML Page ကို Browser ဆီ ပို့မယ်
@app.get("/")
def home():
    return FileResponse("index.html")


# API: Top 10 Score တွေကို ယူမယ်
@app.get("/api/scores")
def list_scores():
    with get_db() as conn:
        rows = conn.execute(
            "SELECT player, score FROM scores ORDER BY score DESC LIMIT 10"
        ).fetchall()
    return [dict(row) for row in rows]


# API: Score အသစ် ထည့်မယ်
@app.post("/api/scores", status_code=201)
def add_score(score: Score):
    with get_db() as conn:
        conn.execute(
            "INSERT INTO scores (player, score) VALUES (?, ?)",
            (score.player, score.score),
        )
    return score
```

**index.html** (ထမင်းစားခန်း)

```html
<!doctype html>
<html>
<head>
  <meta charset="utf-8">
  <title>Game Leaderboard</title>
  <style>
    body { font-family: sans-serif; max-width: 480px; margin: 40px auto; }
    li { padding: 4px 0; }
  </style>
</head>
<body>
  <h1>🏆 Game Leaderboard</h1>

  <form id="score-form">
    <input id="player" placeholder="Player name" required>
    <input id="score" type="number" placeholder="Score" required>
    <button>Add Score</button>
  </form>

  <ol id="board"></ol>

  <script>
    const board = document.getElementById("board");
    const form = document.getElementById("score-form");
    const playerInput = document.getElementById("player");
    const scoreInput = document.getElementById("score");

    // Backend ဆီက Top Score တွေကို တောင်းပြီး ပြမယ်
    async function loadScores() {
      const response = await fetch("/api/scores");
      const scores = await response.json();

      board.innerHTML = "";
      for (const s of scores) {
        const li = document.createElement("li");
        li.textContent = `${s.player} — ${s.score}`;
        board.appendChild(li);
      }
    }

    // Score အသစ်ကို Backend ဆီ ပို့မယ်
    form.addEventListener("submit", async (event) => {
      event.preventDefault();
      await fetch("/api/scores", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({
          player: playerInput.value,
          score: Number(scoreInput.value),
        }),
      });
      form.reset();
      loadScores();
    });

    loadScores();
  </script>
</body>
</html>
```

**Run မယ်**

```bash
cd leaderboard
pip install fastapi uvicorn
uvicorn main:app --reload
```

Browser မှာ `http://127.0.0.1:8000` ကို ဖွင့်ပြီး Score တချို့ ထည့်ကြည့်ပါ။ Leaderboard Update ဖြစ်သွားတာကို တွေ့ရပါမယ်။ Server ကို ရပ်ပြီး ပြန်စကြည့်ပါ - Score တွေက Database ထဲမှာ သိမ်းထားတဲ့အတွက် ရှိနေတုန်းပါပဲ။

**ဘာတွေ ဖြစ်သွားလဲ?**

1. Browser က `/` ကို တောင်းပြီး Backend က `index.html` (**Frontend**) ကို ပို့ပေးတယ်။
2. JavaScript က `GET /api/scores` (**API**) ကို ခေါ်တယ်။
3. Backend က SQLite (**Database**) ထဲကနေ Top Score တွေကို ဖတ်ပြီး JSON ပြန်ပို့တယ်။
4. Form ကို Submit လုပ်လိုက်တဲ့အခါ JavaScript က `POST /api/scores` ပို့ပြီး Backend က Score အသစ်ကို သိမ်းတယ်။

ဒါဟာ Web Application တစ်ခုရဲ့ ပြည့်စုံတဲ့ Life Cycle ပါပဲ။

## ၁၁။ Web Application ကို Deploy လုပ်ခြင်း

တခြားသူတွေ ကိုယ့် App ကို သုံးနိုင်ဖို့ အမြဲဖွင့်ထားပြီး Internet နဲ့ ချိတ်ထားတဲ့ Server ပေါ် တင်ရပါမယ်။ ဒါကို **Deployment** လို့ ခေါ်ပါတယ်။

အသုံးများတဲ့ နည်းလမ်းတွေ -

- **Platform as a Service (PaaS)** – Code ကို Upload လုပ်လိုက်ရင် Platform က Run ပေးပါတယ်။ ဥပမာ: Render, Railway, Heroku, AWS Elastic Beanstalk။
- **Virtual Server** – Server ငှားပြီး အားလုံးကို ကိုယ်တိုင် Setup လုပ်ရပါတယ်။ ဥပမာ: AWS EC2, DigitalOcean။
- **Frontend Hosting** – Static Frontend တွေနဲ့ Next.js လို Framework တွေအတွက်။ ဥပမာ: Vercel, Netlify, AWS Amplify။
- **Container** – App ကို Docker နဲ့ ထုပ်ပိုးပြီး ဘယ်နေရာမှာမဆို Run ပါ ([Docker ဆောင်းပါး](../Docker/docker-and-docker-compose-mm.md) ကို ကြည့်ပါ)။

ဒါ့အပြင် လိုအပ်တာတွေက -

- **Domain Name** (ဥပမာ `myleaderboard.com`)
- **HTTPS Certificate** (Let's Encrypt နဲ့ အခမဲ့ရပြီး Platform အများစုမှာ အလိုအလျောက် ပါပါတယ်)
- **Production Database** (ဥပမာ SQLite အစား PostgreSQL)

## ၁၂။ Web Application Security

Web App တွေက Internet တစ်ခုလုံးကို ဖွင့်ထားတာဖြစ်လို့ Security က မရှိမဖြစ် အရေးကြီးပါတယ်။ အဖြစ်များတဲ့ အန္တရာယ်တွေနဲ့ ကာကွယ်နည်းတွေကတော့ -

| အန္တရာယ် | ဘာဖြစ်လဲ | ကာကွယ်နည်း |
|---|---|---|
| **SQL Injection** | တိုက်ခိုက်သူက Form ထဲမှာ SQL Code ရိုက်ထည့်ပြီး Database ကို ဖတ်တာ ဒါမှမဟုတ် ဖျက်တာ | ကျွန်တော်တို့ ဥပမာမှာလို Parameterized Query (`?` Placeholder) ကို အမြဲသုံးပါ |
| **XSS (Cross-Site Scripting)** | တိုက်ခိုက်သူက Content ထဲ JavaScript ထည့်ပြီး တခြား User တွေရဲ့ Browser မှာ Run စေတာ | ကျွန်တော်တို့ ဥပမာမှာလို User Data အတွက် `innerHTML` အစား `textContent` ကို သုံးပါ၊ Output ကို Escape လုပ်ပါ |
| **Password အားနည်းခြင်း / ခိုးယူခံရခြင်း** | Account တွေကို သိမ်းပိုက်ခံရတယ် | Password တွေကို Hash လုပ်ပါ (bcrypt, Argon2)၊ Plain Text နဲ့ ဘယ်တော့မှ မသိမ်းပါနဲ့၊ 2FA ထည့်ပါ |
| **CSRF** | မသမာတဲ့ Site တစ်ခုက ကိုယ့် Browser ကို လှည့်စားပြီး တခြား Site ဆီ Request ပို့စေတာ | CSRF Token နဲ့ `SameSite` Cookie တွေကို သုံးပါ |
| **Encrypt မလုပ်ဘဲ Data ပို့ခြင်း** | Network ပေါ်က တစ်ယောက်ယောက်က Password နဲ့ Data တွေကို ဖတ်သွားတယ် | HTTPS ကို အမြဲသုံးပါ |

**OWASP Top 10** ဆိုတာ အရေးကြီးဆုံး Web Security Risk တွေရဲ့ နာမည်ကြီး စာရင်းတစ်ခု ဖြစ်ပါတယ်။ တကယ့် App တွေ စတည်ဆောက်တဲ့အခါ တစ်ခေါက် ဖတ်ထားသင့်ပါတယ်။

## ၁၃။ Web App ကို မြန်ဆန်ပြီး Scale လုပ်နိုင်အောင် လုပ်ခြင်း

ကိုယ့် App ကို သုံးတဲ့လူ များလာတဲ့အခါ -

- မကြာခဏ သုံးတဲ့ Data တွေကို **Cache** လုပ်ပါ (ဥပမာ Redis နဲ့)။ ဒါမှ Database ကို အကြိမ်တိုင်း မခေါ်ရတော့ပါဘူး။
- ပုံ၊ CSS နဲ့ JavaScript တွေကို User နဲ့ နီးတဲ့ Server တွေကနေ ပို့ပေးဖို့ **CDN** (Content Delivery Network) ကို သုံးပါ။
- **Load Balancer** နောက်မှာ **Backend Server တွေ ထပ်တိုး** ပါ ([Docker ဆောင်းပါး](../Docker/docker-and-docker-compose-mm.md) ရဲ့ Scaling အပိုင်းကို ကြည့်ပါ)။
- Real-time Feature တွေအတွက် **WebSocket** ကို သုံးပါ ([WebSocket ဆောင်းပါး](../WebSocket/what-is-websocket-mm.md) ကို ကြည့်ပါ)။
- Index တွေနဲ့ ထိရောက်တဲ့ Query တွေနဲ့ **Database ကို Optimize** လုပ်ပါ။

## ၁၄။ Web Development ကို ဘယ်လို စလေ့လာမလဲ?

အသုံးများတဲ့ လေ့လာရေး လမ်းကြောင်း -

1. **HTML နဲ့ CSS** – ရိုးရှင်းတဲ့ Static Page တွေ တည်ဆောက်ပါ။
2. **JavaScript** – Page တွေကို Interactive ဖြစ်အောင် လုပ်ပါ။
3. **Git နဲ့ GitHub** – Code တွေကို သိမ်းပြီး မျှဝေပါ။
4. **Backend Language နဲ့ Framework** – ဥပမာ Python နဲ့ FastAPI ဒါမှမဟုတ် Django၊ ဒါမှမဟုတ် JavaScript နဲ့ Node.js။
5. **Database နဲ့ SQL** – SQLite ဒါမှမဟုတ် PostgreSQL နဲ့ စပါ။
6. **API** – Frontend နဲ့ Backend ကို ချိတ်ဆက်ပါ ([API ဆောင်းပါး](../API/what-is-api-mm.md) ကို ကြည့်ပါ)။
7. **Frontend Framework** – ဥပမာ React ဒါမှမဟုတ် Vue။
8. **Deployment** – ကိုယ့် App ကို Online တင်ပါ၊ ပြီးရင် Docker နဲ့ Cloud ကို လေ့လာပါ။

အကောင်းဆုံး လေ့လာနည်းကတော့ To-do List, Blog, Leaderboard ဒါမှမဟုတ် Chat App လို **Project သေးသေးလေးတွေ တည်ဆောက်ကြည့်တာ** ပါပဲ။

## နိဂုံး

Web Application ဆိုတာ ပြည့်စုံတဲ့ စားသောက်ဆိုင် တစ်ဆိုင်လိုပါပဲ။ **Frontend** က User မြင်ရတဲ့ ထမင်းစားခန်း၊ **Backend** က အလုပ်လုပ်တဲ့ မီးဖိုချောင်၊ **Database** က အရာအားလုံးကို သိမ်းထားတဲ့ သိုလှောင်ခန်းဖြစ်ပြီး **API** ကတော့ အဲဒါတွေကို ချိတ်ဆက်ပေးတဲ့ စားပွဲထိုး ဖြစ်ပါတယ်။

ဒီအစိတ်အပိုင်းတွေ ဘယ်လို ပူးပေါင်းအလုပ်လုပ်လဲဆိုတာ နားလည်သွားပြီဆိုရင် Gmail ကနေ Online Banking အထိ ကိုယ်သုံးနေတဲ့ Web App တော်တော်များများကို နားလည်နိုင်သလို ကိုယ်ပိုင် Web App ကိုလည်း စတင် တည်ဆောက်နိုင်ပါပြီ။

**ကြီးကျယ်တဲ့ Web App တိုင်းဟာ ရိုးရှင်းတဲ့ စိတ်ကူးတစ်ခု၊ Browser တစ်ခုနဲ့ Server တစ်ခုကနေ စတင်ခဲ့တာ ဖြစ်ပါတယ်။**
